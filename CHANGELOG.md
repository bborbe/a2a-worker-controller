# Changelog

All notable changes to this project will be documented in this file.

Please choose versions by [Semantic Versioning](http://semver.org/).

## v0.13.0

- feat: the `local` backend honours a task's own `launcher:` and `role:` frontmatter instead of ignoring both. It exec'd `-local-claude-script` for every tab and never applied a role's chip colour, so `/supervisor:open` — whose create branch routes an absent `target:` here — opened a worker on the vault default while the same task opened through `spawn_agent` got its own launcher, and a controller-opened pane was never coloured by role. **The launcher** now follows the fleet's rule (claude-supervisor `docs/fleet-surface.md` § Spawn a worker, item 8): the task's `launcher:`, else its goals', else the vault's `claude_script`. A task naming its own launcher never reads its goals; a goal link that does not resolve is **skipped with a logged warning** (a stale goal link is a normal vault state, and refusing on one would stop every task carrying it from opening at all); a goal named by a path-qualified wikilink — `[[24 Goals/X]]`, which 11 live tasks carry — resolves against the vault root rather than the goals directory, so the shape is not silently dropped; two goals naming *different* launchers are **refused** rather than resolved by frontmatter order, since list order is not a precedence anyone chose; a bare name resolves beside the vault's own launcher and a value containing `/` is used as given; and anything but a plain path — shell metacharacters, whitespace, a `..` segment — is refused rather than quoted, because frontmatter is writable by supervised workers and the value is exec'd inside `bash -lc`. ⚠️ **The local backend is deliberately STRICTER than `spawn_agent` on this rule, and the divergence is intended.** `server/spawn-cwd.mjs`'s `resolveTaskLauncher` validates the value's *shape* only, because a bad launcher there surfaces as an unreadable `model: null` on the spawn response — an observable that module already reports. This backend has no such observable: `wezterm cli spawn` reports success for a tab whose `exec` then fails, so a typo would produce a **recorded worker whose pane is already gone**, a create that reads as successful and a worker that does not exist. The resolved launcher must therefore be an **executable file** (a directory is refused too, since a mode check alone would admit one), and the refusal happens **before any tab is opened**, leaving no pane behind. The check covers the vault launcher as well as a task's. ⚠️ The resolved value is made **absolute against the vault directory** before either the check or the tab sees it, and that is load-bearing: `tabCommand` builds `cd <vaultDir> && exec <launcher>`, so a relative value would otherwise be stat'ed against the **controller process's** working directory and exec'd against the **vault's** — the check validating a file the tab never runs, in both directions. ⚠️ **The goals directory is read from vault-cli's own config** (`goals_dir`, matched by the vault's `path`, because this backend is configured with a directory and never learns a vault name) rather than hardcoded: it is `24 Goals` in private-personal and `23 Goals` in private-family and private-starcitizen, and a wrong one is not a visible failure — the goal rule simply finds nothing and the worker opens on the vault default, the very silent drop this change removes. When no entry names the vault the rule falls back to `24 Goals` with a logged warning, which costs the goal rule and never a create. **The role** now decides both the window and the chip colour, resolved per create from the WezTerm role map (`~/.cache/wezterm-role-map.json`, overridable with the new `-local-role-map` / `LOCAL_ROLE_MAP`) rather than from the single `LOCAL_WINDOW_ID`, which was the wrong shape for it: measured 2026-10-17, two creates fifteen minutes apart landed in windows 2 and 0, both for `role: agent` rows, so placement was luck. `role:` absent means `agent` and any other value is refused rather than defaulted, because a worker opened in the wrong window with the wrong colour is discovered only by noticing it. An **unusable map is degraded, not refused** — it is published on WezTerm's own reconcile tick, so it is absent on a machine that has never published one — and the caller then falls back to `-local-window-id` and applies no colour, **saying so in a log** rather than silently. ⚠️ Both role-map fields are parsed as **pointers**, so a null or absent value is distinguishable from a zero one: the live map publishes `"Hold": {"chip": null}`, and a plain int would read a missing `window_id` as window **0**, which is the Managers window. The chip is applied by sending `/color <chip>` into the new pane and confirming against the pane's **own output** (the marker `Session color set to`) — never the send's exit code, which is true whether or not the message submitted, and is how a colour came to be reported as applied when it never was (3 of 6 spawns, 2026-09-20). That needed a new `SendText` capability on the `WeztermClient` seam, which activates the pane first (a `send-text` reaches a pane only once its tab is activated), waits for an **empty** composer (the glyph alone appears while the TUI is still painting a placeholder, and a submit sent into that phase is swallowed), submits with a carriage return (a line feed types a break without submitting), and retries the Enter until the marker appears. It is applied **after** the ownership record is written, so a failed write leaves no stray keystrokes on a pane that is about to be killed, and a colour that fails is logged and **non-fatal** — the worker still has its task. The send is bounded by its own deadline, because it holds the backend's mutex: the lock cannot be released mid-send without letting a `stop` kill the pane underneath it, so the bound is what keeps a cosmetic step from blocking `list` and `stop`. The create reply gained `launcher` and `launcher_source` (`task` / `goal` / `vault`), a deliberate widening on the same terms as `pane_id`/`session_id`: a launcher is how a worker was *started*, which any backend that runs a command can answer, and without it a caller has no way to tell which script it got short of reading a process table. Both are empty for a `docker` or `k8s` worker, which runs an image rather than a launcher. ⚠️ An unreadable or unparseable task file is **not** an error on this path: two of the three fields it is read for have a documented default, so such a file degrades to exactly the behaviour that existed before either field was honoured, while refusing would turn it into a create that can never succeed — the same treatment the session-id baseline read already gives it. ⚠️ The frontmatter is parsed as **YAML** rather than line by line, and `goals:` is why: the live vault carries it in the block form (2367 files), the inline flow form (420) and a bare scalar (2), and a goal name itself contains commas ("Supervisor Routes Workers to local, docker or k8s Per Task"), so a reader that split the inline form on its commas would cut the name in two and look up a goal that does not exist.

## v0.12.2

- fix: `create` fails when the WezTerm pane it just spawned has already exited, instead of returning a worker with `state: running` for a dead tab. `wezterm cli spawn` answers with a pane id and succeeds whether or not the tab's command survived — a launcher that dies at once leaves an id WezTerm has already dropped, and nothing in the reply distinguishes the two. Measured live 2026-10-17: a tab running the vault's `cc-private` hit `claude: command not found` (exit 127) while Claude Code was auto-updating, and `create` reported a running worker for a pane that was already gone. The guard waits out a liveness floor after the spawn, re-reading the pane set on an interval derived from that floor and failing the moment the pane is absent — so an instant death costs one listing rather than the whole floor, and a launcher that dies partway through the wait is caught the same way. ⚠️ **The floor is paid on every create, and that is the trade it makes**: up to `DefaultLivenessFloor` (1500 ms) of added latency, bought against a supervisor being told a worker started when its pane is already dead. It is settable as `LocalConfig.LivenessFloor` for a deployment whose launcher settles more slowly. ⚠️ **The check runs before the worker is recorded**, so the failure path writes no store entry — recording first would leave an entry for a pane that is gone, which `list` then reconciles away as a later observation rather than a failure signal at the moment of the call. ⚠️ **A check that failed is not a pane that died**, and the pane is closed whenever the guard cannot reach a verdict — a failed pane listing, or a cancelled wait. Only the confirmed-gone case leaves nothing to close; the other two may leave a live tab, and a pane that is live, unrecorded and unreachable by `stop` is one a retry would duplicate, because the retry finds no entry for the task and passes the dedup. The error reads `pane exited immediately: "<pane-id>"`, deliberately distinct from the existing `spawn worker tab for task %q failed`: the two want opposite retry answers, since a spawn that reported failure may still have opened a pane.

## v0.12.1

- fix: ship `teamvault-cli` in the controller image. The k8s backend resolves a declared secret by shelling out to that CLI, and a scratch image carries nothing it was not given, so a k8s `create` declaring a secret would have failed at its first lookup — after the caller was already told the create succeeded. The docker backend was unaffected: its controller runs on the operator's Mac through the launchd wrapper, which already has the CLI on `PATH`. One image serves both, so the CLI ships in it. ⚠️ **`CGO_ENABLED=0` is load-bearing and its absence fails in a way that reads as a missing file.** `go install` defaults `CGO_ENABLED` to 1, so the binary linked against the system libc; the scratch stage has none, and `exec` reported `no such file or directory` for a file that was plainly present — the build had succeeded and the `COPY` had landed it. Measured 2026-10-17: the image built clean and the CLI still could not run until this was set, which the controller's own build above already does for the same reason. ⚠️ The module path is `github.com/Seibert-Data/teamvault-cli/v5` — the Seibert org, not `bborbe` — and it is pinned to `v5.10.1` rather than `@latest`, so a release tag names a specific artifact instead of producing a different image from the same commit on different days.

## v0.12.0

- feat: `create` accepts caller-declared `mounts` and `secrets`, so a remote worker can reach a vault or a REST endpoint without the caller having to hand it a raw docker argument. A mount is `{host_path, container_path, read_only}` and must fall inside the new `-mount-allow` / `MOUNT_ALLOW` list, a comma-separated set of absolute host-path prefixes parsed like the existing egress allowlist — a malformed entry is refused rather than skipped, and **an empty list allows nothing**, because `create` is a public surface and a forgotten flag must not become an arbitrary-host-path mount. A path outside it is refused with `mount_not_allowed: <path>` and no container is created. ⚠️ **The comparison is on path boundaries, not raw prefixes**: `/srv/data` does not admit `/srv/database`, which is a different directory the operator never named. ⚠️ **A named `volume` is refused outright** (`mount_not_allowed: volume <name>`) rather than ignored — a volume is not a host path, so the allowlist cannot govern it, and a caller free to name one could mount another workload's data volume. The `volume` field exists on the type only so that refusal can name what the caller asked for; Go's decoder drops unknown keys, so an omitted field would have accepted `{"volume": "…"}` and mounted nothing, which reads as success. A secret is `{name, teamvault_key}` and **the value never travels in the request**: the controller resolves the key itself by shelling out to `teamvault-cli password --teamvault-key=<key>`, the same mechanism the launchd wrapper and claude-supervisor's `scripts/mcp-start.py` already use, reading only `TEAMVAULT_CONFIG` so teamvault-cli's own precedence stays the single rule in the system. ⚠️ The resolved value is never logged, and a lookup failure names the **key** and the CLI's stderr — stdout is the secret and is kept in a separate stream precisely so it cannot reach a diagnostic path. ⚠️ **The two backends deliver it differently, and the difference is forced rather than chosen.** Docker writes each value to a 0600 file in a 0700 per-worker directory and bind-mounts it read-only at `/run/secrets/<name>`; an `--env-file` or bare `-e NAME` route was rejected because both land the value in `docker inspect`'s `Config.Env`, where it is readable by anyone with daemon access. The files are removed when the container fails to start and again on `stop`, which is the one place that knows a worker is finished. ⚠️ k8s **cannot** use `secretKeyRef`: the Config CRD's `spec.Env` is a literal `map[string]string`, so a value written there would be a literal in the Config object, durable in etcd. The declared keys are added to the worker's own Secret instead, which the pod already consumes through the `envFrom` the template declares. k8s declares no mount support at all, and a create that asks for one is **refused rather than quietly served without it**. ⚠️ A create that declares a secret on a controller with no TeamVault resolver is refused too, rather than starting a worker that would fail at its first authenticated call — far from the cause, on a surface that already reported success.

## v0.11.0

- feat: `make install` builds, signs and installs the local launchd binary safely, replacing the documented `go install . && cp … ~/.local/bin/` update. The `cp` overwrote the signed binary in place, so the next exec was killed with `SIGKILL (Code Signature Invalid)`; under `KeepAlive` that crash-looped at launchd's 10 s default throttle, which preceded the 2026-10-17 kernel panic. `install` now builds to `<bin>.new`, signs it with the stable `bborbe local codesign` identity (identifier `de.bborbe.a2a-worker-controller`, which also keeps the TCC grant across rebuilds), runs `codesign --verify --strict`, `mv`s it into place, then enforces the launchd baseline on the installed plist (`ThrottleInterval` 30, `SoftResourceLimits.NumberOfFiles` 4096; new idempotent `launchd-baseline` target) and reloads with `bootout` + `bootstrap` (new `launchd-reload` target, which waits for the asynchronous bootout).

## v0.10.0

- feat: a `local` backend runs each worker as a WezTerm tab on the host, so a worker can be an interactive session the operator can watch and drive — the docker and k8s backends run workers as containers and pods, neither of which can open a tab. Selected with `-backend=local`; `create` opens the tab through the vault's `cc-*` launcher and returns the worker carrying its `pane_id`, and `list` reconciles a JSON ownership store against live panes so a controller restart loses nothing. `Worker` gains `pane_id` and `session_id` — a deliberate widening of the shared schema, recorded in `pkg/worker.go` and the README rather than made silently, because a tab worker has no A2A URL and the pane is therefore the only handle a caller can message it through. ⚠️ **`session_id` is empty in the create reply, by design:** the binding is written by the launched session itself, which starts after `wezterm cli spawn` has returned, so `create` reads the task's `claude_session_id` once — usually finding nothing on a fresh spawn — and reports it nowhere. ⚠️ **The worker records the task's `claude_session_id` as it stood at create time as a baseline, and `list` reports a value only once it differs from that baseline**, so a stale id left by an earlier session of the same task is never reported as this worker's. That is what the field being task-scoped makes necessary: the vault stamps it only when it is empty and leaves it alone on every later binding, so without the baseline the backend's own "stop that worker and create another" recovery would report the stopped worker's session for the worker's whole life — a handle that looks valid and resolves to a session that ended. ⚠️ That create-time read is **synchronous, not deferred to `list`**: one file read is not what the caller is waiting on, and an earlier revision of this line claimed otherwise. ⚠️ **Env names from a create request reach a shell command line**, because `wezterm cli spawn` has no env flag and the command line is the only channel: `validateLocalEnv` therefore refuses any name outside `^[A-Za-z_][A-Za-z0-9_]*$`, without which `{"X; rm -rf /": "1"}` would inject shell syntax through the public create API. Env **values** consequently travel in argv and are readable in `ps` for the pane's lifetime — the same property claude-supervisor's own tab path has, and a hard one rather than a shortcut, since the docker backend's `-e NAME` + child-environment trick has no analogue here. ⚠️ **A spawn failure's error names the subcommand only.** The tab's command line is an argv element on this path, so joining the argv into the error — as the docker client's copy of that code does, correctly, because there the command line never reaches argv — would have written a caller's env values, possibly an attention-store token, into the controller's log and Sentry. wezterm's own diagnostic is bounded to its first line for the same reason — a size bound rather than a redaction, since that text is not caller-controlled, but it lands in the same logged message. A worker is keyed on its **GUI instance as well as its pane id**: a pane id is a mux-local counter that restarts with the GUI, so a stale entry would otherwise let `list` name a phantom worker and `stop` kill an unrelated pane. A `task` name is validated before it becomes a task-file path, so it cannot traverse out of the vault, and the work prompt uses the fleet's double-quoted form so a task name containing an apostrophe survives intact.

## v0.9.1

- fix: refuse a `create` for a task that already has a worker, instead of answering with that worker and an empty token. ⚠️ The old reply was **unusable rather than merely incomplete**: every follow-up turn authenticates with the worker's token, the controller keeps no copy of it, and the reply nevertheless read as a success — so the caller was handed a worker it could never reach and had no id to reap it with. Both backends now fail the call, and the controller's log names the existing worker's id. ⚠️ **That id does not reach the caller**: a backend failure is reported as `TASK_STATE_FAILED` with no detail attached, so a caller that must recover — stop the existing worker, then create again — resolves the id itself from `list`, matching on the `task` it asked for. Retrying `create` unchanged on this failure fails identically and forever. One worker per task is unchanged: the refusal starts nothing.

## v0.9.0

- feat: a `create` request can carry environment variables for the worker it starts, so a `target: docker` worker can be handed `POD_ATTENTION_STORE_URL` / `POD_ATTENTION_TOKEN` and raise its permission gate on the attention board. `CreateRequest` gains an `Env` map, and the Docker backend forwards each entry as a **bare** `-e NAME` in argv with the value carried in the child process's environment — so no caller-supplied value, credential or not, is ever readable in `ps`. ⚠️ The uniform treatment is deliberate rather than lazy: the controller cannot tell a credential from a plain setting and `create` is a public surface, so nothing a caller passes reaches argv instead of classifying some entries as safe. ⚠️ **A name the controller sets itself is refused rather than merged**, and the load-bearing one is `AGENT_TYPE` — a caller free to overwrite it could start a worker outside the service path, where no permission decider is wired and the gate this feature exists to deliver would silently disappear. The other eight (`LISTEN`, `A2A_PUBLIC_URL`, `A2A_AGENT_NAME`, `INTERACTIVE_AUTH_TOKEN`, `ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_MODEL`, `ALLOWED_TOOLS`) are refused for the same reason at lower stakes, and a reserved name fails the request **before** a port or a token is minted. Keys are sorted, so an argv built from a map is deterministic and can be asserted rather than merely observed. The k8s backend is untouched: `BuildConfig` takes `(template, workerID, task)` and is never handed the new field, so its render is byte-identical by construction rather than by discipline.

## v0.8.0

- feat: let an `EGRESS_ALLOW` entry name a pod label — `namespace/key=value:port` narrows the rule to pods carrying that label, inside that namespace only. A plain `namespace:port` stays namespace-wide. Needed because on nuke `dev` port 9090 is served by the vault writers and the trading gateways alike, so `dev:9090` would let a worker reach the broker gateways; `dev/app=vault-obsidian-personal:9090` opens the personal vault writer alone. A malformed label is refused, never dropped.
